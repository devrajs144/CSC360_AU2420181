Today's lecture opened with a bit of a roadmap for the rest of the course, laying out the three levels of complexity we'll be working through when it comes to drawing shapes. Starting with a square, moving to a triangle, and eventually working up to trees felt like a natural progression once explained, since each stage seems to build on the coordinate and structural logic covered in earlier lectures. Trees being the final stage suggests we'll eventually be combining multiple shapes and possibly some recursive logic, so that's something to keep in mind as the course moves forward.

From there, the discussion moved into Git practices, specifically the importance of always pulling upstream changes before starting new work. This makes sense in hindsight, since working on an outdated version of the codebase is what usually leads to messy merge conflicts later. It's a simple habit, but one that's easy to forget when jumping straight into coding without checking for updates first.

We then went back into Maven, this time focusing on the role of the `pom.xml` file within a repository. It acts as the core configuration file for a Maven project, defining dependencies and build settings, which ties back to why Maven was installed earlier in the course. Alongside this, we looked at different Maven options available within IntelliJ and how to use them more effectively, which made Maven feel less like a black box and more like a tool with actual visible controls once you know where to look.

The lecture then shifted into a slightly more theoretical direction with a discussion on why GUI components are not thread-safe. This connected to a broader introduction of threads, thread safety, and processes, touching lightly on operating systems concepts. Understanding why GUI operations need to happen on a specific thread, rather than being freely accessed from multiple threads at once, gave some context as to why certain Java GUI code is structured the way it is. This felt like a slightly denser topic compared to earlier sessions, so it's probably worth revisiting once we see it applied directly in code.

Lastly, we touched on why Java has a cold start and why this makes it unsuitable as a scripting language, unlike languages that execute more immediately. This was a shorter point but a useful one, since it explains some of the practical reasoning behind language choice depending on the type of task being performed. Overall, today's lecture felt like it mixed a preview of upcoming graphics work with some foundational computer science concepts that seem to be running in parallel with the main coursework.
